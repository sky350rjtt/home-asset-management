# CHANGELOG.md — HomeAssetManagement 変更履歴

本ドキュメントは2部構成。

1. **バージョン履歴（v1〜v20）**：開発当時の対話記録に基づく正式な履歴（ユーザー提供、2026-08-12時点）。
   コードのコメントには残っていない情報のため、これを一次情報として採用する。
   一部の版（特に v19・v20）は `src/` 内のコード内コメント（`★V19`, `★V20` 等）でも直接裏付けが取れており、
   該当箇所は引用を添えている。それ以外の版は対話記録のみが根拠であり、簡素な説明にとどめている行は
   無理に詳細化していない。
2. **改善履歴（v20以降）**：v20を正式リリース版・現行稼働バージョンとして固定し、それ以降の変更は
   バージョン番号を振らず、日付ベースで積み重ねる形式に切り替える。

> **注記（2026-08-12）**：本ドキュメントが引用している `★V19`/`★V20` 等のコード内コメントは、
> このドキュメント作成後に実施したコメント整理（改定過程の痕跡を除去し、ロジック説明のみに
> 書き直す作業）で `src/` から削除・書き換えされている。したがって、現在の `src/` を検索しても
> ここに引用した文言そのものは見つからない。引用は「その時点でコードに残っていた記録」としての
> 歴史的な証跡であり、現行コードの記述とは一致しない場合がある。

### v1〜v5：初期設計・家電管理の基本機能

対話記録のみが根拠。現行コードとの対応関係を裏付ける具体的なコメントは残っていない。

### v6：INBOX一本化・同一バッチ設計

INBOX配下のフォルダ構成（`ADD/` と拠点フォルダ）に投入されたファイルを1つの入口（`INBOX_FOLDER_ID`）に
一本化し、バッチ単位で処理する設計の原型。現行の `Scanner.gs` がINBOX直下のサブフォルダを走査し、
フォルダ名によって `AddFolder.process()` / `Location.process()` に振り分ける構造は、この時点の設計を踏襲している。

### v7〜v11：差分改修（Config外部化・購入情報自動抽出等）

- **Config外部化**：フォルダID・APIキー等のインフラ設定をコードから切り離し、`Config` シート（A列＝キー、
  B列＝値）から読み込む方式へ移行。現行の `Config.gs` の原型にあたる。
- **購入情報自動抽出**：領収書・保証書からGeminiが `purchaseDate`/`purchasePrice`/`purchaseStore`/
  `warrantyExpiry` を抽出し、台帳（J〜M列）へ書き込む機能。現行の `AssetMasterDAO.updatePurchaseInfo()`
  （既存セルが空のときだけ上書きする設計）の原型にあたる。

### v12：全差分を統合した完全版

v7〜v11の各差分改修を1つの完全版としてまとめた版。対話記録のみが根拠。

### v13：LockService・リトライ・JPEG/PNG・HEIC対応

- **LockService**：二重実行防止。現行の `Scanner.run()` が `LockService.getScriptLock()` +
  `waitLock(10000)` で「メニューとWebAppから同時に実行された場合」の競合を防いでいる部分に対応。
- **リトライ**：Gemini API通信の失敗時再試行。現行の `Gemini.gs` の `generateContent` 呼び出しが
  429/5xxエラー時に最大3回まで指数バックオフでリトライする実装、およびファイルの`ACTIVE`化を
  最大36回×5秒ポーリングして待つ実装に対応。
- **JPEG/PNG・HEIC対応**：現行の `Constants.SUPPORTED_MIME`（PDF/JPEG/PNG）と `Constants.MIME_HEIC`、
  `FileUtils.getSupportedFiles()` のHEIC検出、`Scanner.gs` のHEICスキップ件数レポート機能に対応。

### v14：Geminiモデル・カテゴリをConfigシートで管理

- 解析に使うAIモデル名（`GEMINI_MODEL`）と、資産のカテゴリ一覧を、コードのハードコードではなく
  Configシート／Mastersシート側で管理する方式へ変更。現行の `Config.load()` の `GEMINI_MODEL` 読み込みと、
  `MastersDAO.load()` の `CATEGORY_` セクション読み込みに対応する。
- 現行コードでは、Configシートの `GEMINI_MODEL` 行はドロップダウン（データ入力規則）で選択させる方式に
  なっており、`Entry.gs` の `getModelSettings()` / `_writeConfigValue()` はこの行を固定の行位置ではなく
  キー名で検索して読み書きする（Configの行を増減しても壊れない設計）。この「キー名で探す」実装が
  この版で入ったものか、後の改修で追加されたものかは対話記録・コードコメントのいずれからも特定できない。

### v15：INBOXサブフォルダ自動判定・1ボタン化

INBOX配下のサブフォルダ名を見て、`ADD`（既存資産への追加）か拠点コード（新規登録）かを自動判定する
方式を確立し、ユーザー操作を「Scan & Execute」1ボタンに集約。現行の `Scanner._execute()` の
サブフォルダ判定ロジックと、`Index.html` の単一ボタンUIに対応する。

### v16：重複検出バグ修正・不要コード削除・最適化

現行の `FileUtils.getSupportedFiles()` が `Set` (`seen`) でファイルIDの重複を排除しているのは、
同一ファイルを二重処理してしまう不具合への対策と考えられる。それ以外の詳細は対話記録のみが根拠。

### v17：可読性重視・WebApp対応・コメント充実

- **WebApp対応**：`Entry.gs` の `doGet(e)` が `p` パラメータで `Index.html`（スキャン実行画面）と
  `index_viewer.html`（Viewer画面）を切り替える、現行のマルチ画面ルーティングの原型。
- **コメント充実**：`src/` 内の各ファイルに残る、役割・責任・流用可否・他モジュールへの依存を記した
  日本語のヘッダーコメント群は、この時期の方針を踏襲していると考えられる。

### v18：疎結合設計・DAO導入・名前空間・処理/マスタ/データ分離

`ARCHITECTURE.md` 1.1節で整理した設計原則（処理・マスタ・データの分離）そのものが確立した版。

- **DAO導入**：台帳への読み書きを `AssetMasterDAO.gs`、マスタの読み込みを `MastersDAO.gs` として
  独立させ、「台帳の列配置(COL/DOC_COL)を知ってよいのはDAOだけ」という分離を確立。
- **名前空間**：`Config` / `MastersDAO` / `AssetMasterDAO` を即時実行関数（IIFE）`const X = (() => {...})();`
  で包み、内部状態（`_cache`, `_getSheet` 等）を外部から触れなくする現行のカプセル化パターンの原型。

### v19：Blob化・buildFileName配列化・log配列化・isValidCategory追加・カプセル化強化

- **Blob化**：Gemini解析対象をファイルの生バイナリ（Blob）で扱う方式。現行の `Gemini.analyze()` が
  `Blob|Blob[]` を受け取り、`Location.gs`/`AddFolder.gs` が `file.getBlob()` で渡す実装に対応。
- **buildFileName配列化**：ファイル名を構成するパーツを配列で受け取り結合する方式。現行の
  `FileUtils.buildFileName(parts, ext)` のJSDocに「`@param {string[]} parts` - ファイル名を構成する
  パーツの配列」と明記されている実装に対応。
- **log配列化**：ログ1行分のデータを配列で渡す方式。現行の `SheetUtils.log(sheet, dataParts)` に対応。
- **isValidCategory追加**：Geminiが返したカテゴリコードが不正な場合に `OTH` へ補正する
  `MastersDAO.isValidCategory()` の追加。現行の `Location.gs`/`AddFolder.gs` の
  「不正なカテゴリコード: ... → OTH に補正」ログに対応。
- **カプセル化強化**：v18で導入したDAOを、さらに「思考停止」（渡された値をそのまま書き込むだけで
  業務判断を持たない）な設計へ寄せていく流れに対応すると考えられる。現行の `AssetMasterDAO.gs` に残る
  「★DAOは思考停止で、渡された embedding の数値をそのままT列に突っ込むだけ」「★S/T列は物理的に隣接
  (19,20)しているため、getRange(row,19,1,2)で一括更新できる」というコメントは、この方向性のもとで
  行われた最適化と考えられる（ただし、これらのコメント自体にバージョン番号の明記は無いため、確定はできない）。
- **既知の不具合（V19時点）**：`ADD/`フォルダ経由で取説(MNL)を既存資産に後から追加しても、検索用の
  remarks(S列)・ベクトル(T列)が更新されなかった（出典：`src/maintenance/RemarksBatch.gs` 冒頭コメント
  「AddFolder.gsの穴（V19以前は取説を後から追加してもベクトルが更新されなかった）」）。

### v20：マルチファイル対応・ベクトル検索実装・命名規則刷新・typeCode廃止・AddFolder取説追加時の再ベクトル化（正式リリース版）

対話記録とコード内コメントの双方から裏付けが取れる、最も情報量の多い版。**このシステムの現行稼働バージョン**。

- **マルチファイル対応**：説明書・保証書・領収書など、同一資産の複数ファイルを1リクエストにまとめて
  Geminiへ渡し、統合解析させる方式へ刷新。`AddFolder.gs` のコメント「★【大変更】プロンプトを
  『マルチファイル・ファイル名マッピング仕様』へ完全同期！これにより、複数ファイルを同時に投げた際、
  どのファイルがMNLで、どれがRCPかをAIが正しく識別します」に対応。`Gemini.analyze()` の
  `fileContext`（一時URIと元ファイル名の対応表をプロンプト先頭に付加する仕組み）もこの一環。
- **ベクトル検索実装**：`Gemini.embed()` によるテキストのベクトル化、`VectorMaintenance.gs` による
  ベクトル化用テキストの組み立て、台帳T列への格納、`IntelligentSearch.gs` による総当たりコサイン類似度
  検索一式が、この版で新規実装された。`Location.gs` のコメント「★新規追加：拠点フリー・カテゴリコード
  フリーのクリーンな検索用ベクトルをその場で生成」「★大修正：削ぎ落とされたクリーンな DAO 側の insert
  に対し、remarks と embedding の双方を渡して一発書き込み」に対応。実装後の細かな最適化（台帳読み込みと
  ベクトル取得を1回にまとめ、以前の「IDの再マッチング」処理を廃止したこと、検索結果の足切りスコア閾値を
  `Config.SEARCH_MIN_SCORE` としてConfigシート駆動にしたこと）も、`IntelligentSearch.gs` のコメントから
  同じ v20 の実装過程の一部と判断できる。
- **命名規則刷新（拠点+カテゴリ+年+連番）**：資産IDを `{拠点コード}{カテゴリコード}{西暦下2桁}{連番3桁}`
  （例: `H01REF26001`）へ刷新。現行の `AssetMasterDAO.assignId()` の採番方式（詳細は `SPEC.md` 5章）。
- **typeCode廃止**：assetId自体にカテゴリコード（`REF`等）が含まれるようになったため、ファイル名の
  構成パーツから独立した `category`（typeCode相当）を排除。`AddFolder.gs` のコメント「★【大変更】
  assetId自体にカテゴリ(REF等)が含まれるため、配列からcategoryを完全に排除！これにより、
  `H01REF26001_Toshiba_...` という無駄のないファイル名になります」に対応。
- **AddFolder取説追加時の再ベクトル化**：`ADD/`フォルダ経由で取説(MNL)が追加された場合に限り、
  remarks/検索ベクトルを再生成する機能。`AddFolder.gs` 冒頭コメント「取説(MNL)が追加された場合のみ、
  remarks/検索ベクトルを再生成する ★V20で追加」に明記。V19時点の不具合（上記）を解消する変更であり、
  追加のGemini呼び出しは不要で、その回のバッチ処理で既に解析済みの `info.remarks`/`info.summary` を
  使い回して組み立て・埋め込みのみを行う。V19時点で取り残された過去データを復旧するための保守バッチ
  `RemarksBatch.gs`（`GENERATE_EMBEDDINGS_FROM_ACTUAL_PDFS`）もあわせて用意された。
- **その他プロンプトの調整**：`Location.gs` に残る「★【プロンプトの超調教】トースターやシュレッダーの
  誤浮上を根絶する『ノイズ完全排除令』をインジェクション」というコメントも、この版でのプロンプト
  全面刷新の一環と考えられる。

## 改善履歴（v20以降・バージョン番号なし）

v20を現行稼働バージョンとして固定した後の変更は、バージョン番号を振らず日付ベースで記録する。

### 2026-08-12

`docs/SPEC.md` ・`docs/ARCHITECTURE.md` の整備を通じて洗い出したリファクタリング候補のうち、
優先度が高いと判断された3件を実施。

1. **ID採番のfail-fast化**（`dao/AssetMasterDAO.gs` の `assignId()`）
   - 資産IDの期待文字列長を `11` のハードコードから `prefix.length + SEQ_DIGITS` の動的算出に変更。
     将来、拠点コード・カテゴリコードの文字数が変わっても追従できるようにした。
   - 連番が3桁の上限（999）を超える場合や、拠点コード・カテゴリコードが空の場合に、
     黙って処理を続けず例外を投げるようにした（以前は採番の前提が崩れた際、IDが静かに衝突しうる
     設計だった）。
2. **プロンプトの共通化**（新規 `shared/PromptBuilder.gs`）
   - `Location.gs`（新規登録）と`AddFolder.gs`（既存資産への追加）に別々に存在していた
     Gemini解析プロンプト全文（大半が一字一句同一だった）を、共通の組み立てロジックへ集約。
   - 統合時に見つかった、意図的な使い分けとは考えにくい表記ゆれ（`modelNumber`のラベル列挙の
     全角/半角スペース違い、`summary`指示の詳しさの違い、末尾`CRITICAL`行の分裂）は、
     人間による書き分けのズレと判断し、意図を汲んで1本の文言に統合した。
   - `Constants.gs`（「完全流用可」の前提を持つファイル）に業務ルールを混入させないよう、
     あえて`shared/`配下の別ファイルとして切り出した。
3. **依存の向きの是正**（新規 `shared/AssetPresenter.gs`）
   - `logic/IntelligentSearch.gs` が `ui/Entry.gs` 内のグローバル関数 `_loadAssetsFromLedger()` を
     直接呼び出す「ロジック層がUI層に依存する」逆依存を解消。
   - 台帳の読み込み・画面表示用整形ロジックを `AssetPresenter.gs` に切り出し、`Entry.gs`と
     `IntelligentSearch.gs`の双方がそこに一方向で依存する形に整理。`includeEmbedding`引数による
     不要データ転送カット（Viewer初期表示では軽量版、AI検索ではベクトル付き）は変更せず維持した。

## 付録：バージョンを特定できない変更（★マークのみ、コード内コメントより）

以下は `src/` のコード内コメントに残っているものの、上記のv1〜v20のどの版に属するかを
対話記録・コードコメントのいずれからも確定できない変更点。無理に版を割り当てず、参考情報として記載する。

- **`core/Gemini.gs` の安定化**：ダブルクォーテーションの競合を解消した「修正版」への置き換え
  （コメント：「★ 修正版：ダブルクォーテーションの競合を解消」）、マークダウンの ` ```json ` フェンスを
  弾く安全パースを「完全死守」する方針（コメント：「★ マークダウンの```jsonを確実に弾く、あなたオリジナル
  の安全パースを完全死守！」）、大容量ファイル対応のストリームアップロード仕様を「完全死守」する方針
  （コメント：「★ 24MBのパンクを防ぐ、あなたオリジナルのストリーム仕様を完全死守！」）。
- **`ui/index_viewer.html` の検索UX強化**：検索クエリとローカル台帳データの双方に適用する正規化エンジン
  （全角/半角統一、ひらがな→カタカナ統一、大文字小文字統一、法人格ノイズ除去、空白除去）の新規追加
  （コメント：「🚀【新規追加】最強の検索正規化（前処理クレンジング）エンジン」）。
