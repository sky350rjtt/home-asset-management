# FRONTEND_PHILOSOPHY.md — フロントエンド設計思想

> **このドキュメントの位置づけ**
> HomeAssetManagement(GAS版)の`index_viewer.html`で確立した、フロントエンド設計の思想・パターン集。
> 技術基盤(GAS → Next.js/Supabase等)が変わっても、**この思想はそのまま持ち越す**。
> 次のプロジェクト(鉄道電光掲示板・不動産管理システム)でも、この文書を土台に議論を始める。

---

## 1. 大原則:検索前提設計

```
このシステムは「一覧をスクロールして探す」ものではなく
「検索して一発で当てる」ものとして設計する
```

**理由**：件数が数十件でも数百件でも、UXの正解は変わらない。一覧性を高める施策(カード高さを詰める等)より、**検索・フィルタの精度と速度に投資する**。

### 派生する設計判断
- 初期表示を全件出すか空にするかは、**利用規模で決める**(家庭用=全件表示可、業務用=空スタート推奨)
- カードの情報密度より、検索窓・フィルタチップの使いやすさを優先する

---

## 2. ローカル検索 → AIフォールバックの直列構成

```
① ブラウザ側で保持しているデータに対する部分一致検索を先に試す
② ①が0件のときだけ、サーバー側のベクトル(意味)検索を呼ぶ
```

**理由**：件数がスケールしても、ほとんどの検索はローカルの文字列一致で解決する。AI検索はコストが高い(レイテンシ・API課金)ため、**必要な時だけ発動する設計にする**。

### 注意点(実際に起きた事故)
AI検索の結果は「関連度順」に意味があるため、**ローカルソート処理で結果の並びを勝手に上書きしてはいけない**。AI検索が成功した際は、ソートUIを「関連度・登録順」に強制し、フロント側の`.sort()`をスキップする分岐を必ず設ける。

---

## 3. 表記ゆれの正規化はフロント・サーバー両方で同じロジックを使う

```
全角/半角、ひらがな/カタカナ、大文字/小文字、法人格表記(株式会社等)の
ノイズを除去してから比較する
```

**理由**：検索語と検索対象データ、双方を同じルールで正規化しないと、片方だけ揺れを吸収できず検索漏れが起きる。この正規化関数(`normalizeText`)は、**フロントとサーバーで実装を分けず、可能な限り共有する**(Next.js移行後は`lib/utils/normalizeText.ts`のような共通モジュールに)。

---

## 4. 色は装飾、情報は色に依存させない

```
色だけで状態を伝えない。必ずテキスト・アイコン・title属性(または
aria-label)を併記する
```

**確定した運用**：
- カードの背景色に意味を持たせない(NotebookLM風のランダム色分けは不採用。グレー統一)
- 稼働ステータスは「色付きランプ」+「title属性」の組み合わせで表現する(色だけに依存しない)
- 書類種別はアイコン+テキストラベルの組み合わせ(アイコン単体は不可、後述7章)

---

## 5. 情報のメタ性で配置場所を決める

```
識別子(ID)     → カード右上に固定配置
状態(稼働/除外) → 左上のインジケーターランプ + IDへの併記
本体情報(製品名等) → カード中央、最も目立つ位置
メタ情報(購入日等) → 下部、常に固定の高さを持たせる
```

**理由**：情報の「性質」によって視線誘導の優先順位が決まる。IDは"識別のための値"であり、"内容を説明する情報"(製品名・メーカー)とは性質が違うため、明確に分離した位置に置く。

### 高さを揃える設計原則
可変長の情報(書類の数、購入日の有無等)は、**カード本体の高さに影響させない**。
- 書類ボタン→横スクロール帯として下部に独立させる(縦積みにしない)
- 値がない項目→空の行を出力して高さだけ確保する(行ごと消さない)

> **(2026-08-14 改訂)** 「書類ボタンの横スクロール帯」は第14章の原則により撤回した。
> 一覧カードからは書類ボタンごと撤去し、詳細シートに集約する方式に変更した。
> 高さを揃える設計原則そのもの(可変長情報でカード高さを変えない)は有効なまま。

## 6. マジックナンバー・重複ロジックの排除(DRY)

```
同じ判定ロジック、同じ数値は、1箇所の関数・定数にまとめる
```

**実例**：
- `isAssetActive()`判定を、フィルタリング処理と描画処理の2箇所に別々に書かない。共通のヘルパー関数に集約する
- ボタン幅・レイアウト定数は、CSSクラスや定数として1箇所にまとめ、複数箇所への直書きを避ける

**Supabase移行後の対応**：Reactではこれが「カスタムフック」や「ユーティリティ関数」として、より自然に実現できる。GAS版で意識的に守ってきたこの原則を、コンポーネント設計の初期段階から徹底する。

---

## 7. アイコンは絵文字ではなくアイコンフォント/SVGを使う

```
OS依存でトーン&マナーが崩れる絵文字(📄🧾🛡️)は使わない
Material Symbols等の統一されたアイコンセットを使う
```

**理由**：絵文字はOS・ブラウザによって見た目が変わり、ダークモードでの色調整もできない。業務システムとしての一貫性を保てない。

### アクセシビリティ対応とセット
アイコン単体では意味が伝わらないため、**必ずテキストラベルを併記する**か、アイコンに`aria-hidden="true"`を付けた上で親要素に`aria-label`を持たせる。装飾目的のアイコンは常に`aria-hidden="true"`にする。

---

## 8. セマンティックHTML・アクセシビリティの最低ライン

2026年時点、WCAG 2.2準拠(JIS Aシングル相当)は日本国内でも事実上の標準要件(2024年障害者差別解消法改正により義務化)。GASという制約下でも、以下は必ず実施する。

### 必須対応
- `<div>`の乱用を避け、`<header>`・`<main>`・`<search>`・`<fieldset>`等、意味を持つタグを使う
- 検索窓・セレクトボックスには`<label>`(視覚的に隠す場合は`.sr-only`)を必ず紐付ける
- 装飾アイコンには`aria-hidden="true"`、機能アイコンには`aria-label`
- クリックだけで完結するUI部品(フィルターチップ等)は`<div onclick>`ではなく`<button>`にし、キーボード操作(Tab/Enter/Space)を保証する
- 開閉するUI(詳細フィルター等)は`aria-expanded`/`aria-controls`で状態を伝える
- 動的に更新される領域(検索結果・件数表示)は`aria-live`/`aria-busy`で状態変化を通知する

### GASの制約により対応しないこと(意図的な判断)
- **多言語対応(i18n)**：家庭用・国内業務用途であり、必要性が薄い。実装コストに見合わない
- **AVIF/WebP画像最適化**：システム内で写真・画像を扱わない設計のため該当なし
- **Service Workerによる本格PWA化**：GAS配信のHTMLではスコープ制約により実質困難。簡易メタタグ対応に留める

---

## 9. フロント/バックエンド分離は「格」を揃えてから行う

```
本格的なフロント(独自ドメイン・Cloudflare等)を用意するなら、
バックエンドも同じ「格」(認証・API・DB)を持たせる
```

**教訓**：GAS+Sheetsという「個人効率化ツールの格」のバックエンドに、Cloudflare Pagesという「業務システムの格」のフロントを接続しようとして、認証・CORS・API化のコストが雪だるま式に膨らんだ。**フロントとバックエンドの技術的な「格」は揃える**。片方だけ先行して本格化させない。

→ この教訓が、Supabase移行(フロント・バックエンドを同時に本格化させる)の直接的な動機になっている。

---

## 10. BFF的発想:フロントに機密を持たせない

```
APIキー・シークレットの類は、フロントエンドのコードに
一切含めない
```

GAS版では「Config.load()」経由でバックエンド側にのみAPIキーを持たせ、フロント(HTML/JS)には一切露出させない設計を貫いた。これは2026年の業界警告(ブラウザから直接SaaS APIを叩く構成の危険性、過剰なデータ露出リスク)を、意図せず先取りして回避していた。

**Supabase移行後も同じ原則を維持する**：Supabaseの`service_role`キーのような強い権限を持つ鍵は、絶対にフロントのコードに含めない。フロントが直接触れてよいのは`anon`キー(RLSで保護された範囲)のみ。

---

## 11. Supabase移行時の対応表(思想の引き継ぎ方)

| GAS版での実装 | Supabase/Next.js版での対応 |
|---|---|
| `google.script.run`経由の呼び出し | Server Actions / API Routes経由のfetch |
| `normalizeText()`(フロントJS内) | `lib/utils/normalizeText.ts`として共通化、フロント・バックエンド両方から呼べる形に |
| ローカル検索→AIフォールバックの直列構成 | 同じ構成を維持。ローカルはクライアント側state、AI検索はSupabase Edge Function経由のベクトル検索(pgvector) |
| `isAssetActive()`等の共通判定ロジック | カスタムフック(`useAssetStatus`等)として実装 |
| Material Symbols(Webフォント) | 同じくWebフォント、またはSVGアイコンコンポーネント化 |
| `aria-*`属性の手書き | 変わらず必須。shadcn/ui等のコンポーネントライブラリを使う場合も、アクセシビリティ属性が正しく機能しているか個別に確認する |
| GASの「格」の制約(認証・API貧弱) | Supabase Authで解消。ただし「フロントとバックエンドの格を揃える」という原則そのものは、常に意識し続ける |

## 12. UD準拠(土台)とブランドの個性(上物)は両立できる

```
UD/アクセシビリティ = 「土台」（守るべき最低ライン、規格に正解がある）
ブランドの個性       = 「上物」（土台の上に積む、正解のない領域）
```

GoogleのMaterial DesignもAppleのHuman Interface Guidelinesも、WCAG準拠を土台にした上で、「丸み」「余白」「タイポグラフィ」「モーションの質感」でブランドらしさを表現している。**UDと個性は対立しない。土台と上物の関係。**

### 土台(触ってはいけない、規格準拠)
- コントラスト比(4.5:1以上)
- タップ領域のサイズ(44px以上)
- キーボード操作性・スクリーンリーダー対応
- 色だけに依存しない情報伝達

### 上物(ブランドの個性を乗せてよい領域)
- 角の丸み、余白の取り方
- タイポグラフィ(フォント・太さ)
- カラーパレット(コントラスト比さえ守れば自由)
- モーション・アニメーションの質感
- アイコンのスタイル(丸み・線の太さ)

### 今回のシステムで、既に無意識に選んでいた"上物"の方向性
- グレー統一(NotebookLM風のランダム色分けを却下) → 実用性優先というブランドの一貫性
- 書類ボタンの横スクロール化(※2026-08-14撤回、第14章参照)、IDの右上固定配置 → 機能的で整然とした世界観
- Material Symbolsによるアイコン統一 → 装飾より統一感を選ぶ美的判断

これらは規格が導いた答えではなく、**「機能美・信頼感・堅実さ」という、あなた自身が一貫して選んできた美的方向性**である。事業化する際は、この無意識の選択を、意図的なブランドガイドライン(色数を絞る、角丸の数値を統一する等の2〜3個の一貫したルール)として言語化するところから始める。

## 13. 汎用ツールの劣化コピーにならないための原則

### 気づきの経緯

UIをGoogle検索・Notion・NotebookLM等の優れたパターンに寄せ続けた結果、「これを極めていくと、行き着く先はNotionやNotebookLMそのものになり、それらを使えばいいのでは」という懸念に至った。特に「ユーザー認証」「登録処理の統合」「複数人での管理」といったバックエンド機能を足し始めると、この懸念は現実味を帯びる。

### 結論:ターゲットユーザーが最初から違う

```
Notion / NotebookLM が機能するユーザー:
  ・自分でデータベースのプロパティを設計できる
  ・型番や保証期限を、手入力する手間を厭わない
  ・「汎用ツールを自分好みにカスタマイズする」こと自体に
    価値を感じる、リテラシーの高い層

このシステムが向いているユーザー:
  ・そもそも汎用ツールのセットアップというハードル自体を
    越えられない、または越えたくない層
  ・「PDFを放り込むだけで、あとは全部AIが勝手にやってくれる」
    という"考えなくていい"体験を求める層
  ・知識のない家族など、汎用ツールを渡しても使いこなせない人たち
```

**UIの型(検索窓・フィルター・カード表示)が既存の優良製品に似るのは必然であり、失敗ではない。** 「情報を検索して閲覧する」というタスクにおける優れたUXパターンの選択肢は収束しており、真剣に追求すれば既存製品に似てくるのは当然。UIが似ることと、システムの存在価値がなくなることは別の話である。

問題になるのは、UIではなく**機能**を汎用ツールに寄せていく場合である。認証・共同編集・ページ間リンク・コメント機能といった汎用コラボレーション機能を後から足していくと、Notionの機能を1つずつ劣化コピーで再実装することになる。これは避けるべき方向性。

### 機能追加の判断基準

新しい機能を追加するかどうか迷ったら、以下を自問する。

```
Q1: この機能は、Gemini等による自動化という
    このシステム固有の強みを伸ばすか?
    (例: 型番・カテゴリの自動抽出、
     あいまい検索ワードの自動生成、ベクトル検索)

Q2: それとも、Notion/NotebookLM等が既に持つ汎用機能
    (認証、権限管理、共同編集、ページリンク、
     コメント機能等)を、劣化した形で再発明しようと
    しているだけか?
```

**Q2に該当すると判断したら、その機能は追加しない。** 「それが必要な人はNotion/NotebookLMを使えばいい」という判断を、迷わず受け入れる。競合しているのではなく、Notionが相手にしていない市場(汎用ツールを使いこなせない・使いこなしたくない層)を相手にしている、という位置づけを見失わない。

### 例外的に許容してよい最低限の機能

「誰が登録したか」を記録する程度の、ごく軽い認証(閲覧権限の絞り込み)は、汎用コラボ機能ではなく「家族専用アプリとしての最低限のプライバシー確保」として許容範囲。危険なのは、そこから「誰が」「いつ」「どんな権限で」という汎用的なマルチユーザー管理の概念が芋づる式に膨らんでいくこと。

## 14. 一覧は「探すための情報」のみ、詳細は専用シートに分離する

```
一覧カードに置いてよいのは、検索・識別のために必要な情報だけ
(状態ランプ・カテゴリ・製品名・メーカー/型番)

それ以外(ID・拠点・購入日・書類等の"見るための情報")は
一覧に置かず、タップして開く詳細シートに集約する
```

**理由**：第1章の大原則(検索前提設計)の帰結。一覧の役目は「探し出して当てる」ことであり、
「すべての情報をその場で見せる」ことではない。一覧カードに情報を詰め込むほど、1枚あたりの
認知負荷が上がり、かえって探しにくくなる。

### 教訓:補助表示が必要になった時点で、一覧内の設計は間違っている
5章・12章で「良い設計」として記載していた「書類ボタンの横スクロール帯」は、後に撤回した。
横スクロールを機能させるには、エッジフェード(端が切れていると気づかせる装飾)・件数バッジ・
スクロール位置の実測ロジックといった**補助表示**が次々に必要になった。この「補助表示が要る」
という事実自体が、一覧カードにその情報を置くべきではなかったことの兆候である。

```
補助表示(フェード・件数バッジ等)を追加しないと使えないUIは、
一覧に置く情報の選定を間違えている
```

一覧内で完結させようとする限り、この種の補助UIは際限なく増えていく。正しい対処は補助表示を
洗練させることではなく、**そもそもその情報を一覧から追い出し、詳細ビューに任せる**こと。
縦に開く詳細シートであれば、横スクロール・エッジフェード・件数バッジのいずれも不要になる
(内容を上から下に並べればよいだけになるため)。

### 派生する設計判断
- 新しい情報項目を追加したくなったら、まず「これは検索・識別に要るか」を自問する。Noなら詳細側に置く
- 一覧側のカードにpadding・truncate・エッジフェード等の補助CSSが増え始めたら、情報過多の兆候として
  疑ってよい
- 詳細シートは「一覧に入りきらなかった情報の置き場」ではなく、「一覧が担わない役割(閲覧・内容確認)を
  専任で担う場所」として設計する

## まとめ:持ち越すべき核心

```
① 検索前提・AI依存の直列フォールバック設計
② 色に依存しない情報設計 + セマンティック/アクセシビリティの徹底
③ フロントとバックエンドの「格」を常に揃える
④ UD準拠を土台とし、その上にブランドの個性を積む(対立させない)
⑤ 汎用ツールの劣化コピーにならない(ターゲットユーザーの違いを見失わない)
⑥ 一覧は「探すための情報」のみ、詳細は専用シートに分離する
   (補助表示が要るUIは、一覧側の情報選定そのものが間違っている合図)
```

技術基盤(GAS/Cloudflare/Supabase)は入れ替わっても、**この6つの思想は、次のどのプロジェクトでも最初に確認すべき前提として持ち越す**。
